# SGI O2 (IP32, "Moosehead") — design and bring-up plan

IRIS emulator support for the SGI O2. This document is the plan of record:
what the machine is, how it maps onto the existing emulator, and the order
the work lands in.

Authoritative sources, in the order we trust them:

1. The leaked IRIX 6.5.7m source tree (`kern/sys/crime.h`, `kern/sys/mace.h`,
   `kern/sys/ds17287.h`, `kern/sys/IP32.h`, `kern/ml/MOOSEHEAD/*`, and the
   `stand/arcs/IP32prom` firmware source) — the firmware and the kernel are
   the only things that have to run.
2. The O2 hardware manuals in `docs/o2/` (crime1_5.pdf, gbe.pdf, mace.pdf,
   vice.pdf, AIC-7850/7870 data books).
3. Linux/NetBSD drivers, for cross-checking register semantics.

## 1. What the machine is

The O2 is not an Indy/Indigo2 variant. It is a different system ASIC set, and
nothing in the IP22/IP24/IP28 device model transfers:

| | Indy/Indigo2 (IP22/IP24/IP28) | O2 (IP32) |
|---|---|---|
| System ASIC | HPC3 + IOC2 (+ MC on Indigo2) | **MACE** |
| Memory + interrupt controller | MC (MEMCFG0/1) + IOC2 | **CRIME** |
| Graphics | GIO64 board (REX3/GE7/GE11) | **CRIME** graphics: MRE rasterizer + **GBE** display engine |
| Video | VINO / Indy cam | MACE VIN1/VIN2/VOUT |
| SCSI | WD33C93A on HPC3 | AIC-7880 on the MACE PCI bridge |
| Ethernet | SEEQ 8003 on HPC3 | MAC110 in MACE |
| Audio | HAL2 | MACE audio + AD1843 codec |
| Console | graphics (Newport) or Z8530 SCC | graphics (CRM) or MACE 16550 UART |

"CRIME" is the whole graphics ASIC, not just its display half. Its parts,
as the hardware names them:

| Part | Role |
|---|---|
| CRIME CPU interface | geometry setup, memory controller, interrupt controller, timer |
| **MRE** (Media Raster Engine) | rasterizer + texture mapper, driven through the CRIME register file at `0x15000000` |
| **GBE** (Graphics Backend) | the display engine: video timing, tile-based framebuffer, WID/DID, cmap/gamma, cursor — the part that scans the framebuffer out to the monitor |
| **VICE** (ICE) | image-compression accelerator, IRIX-only, not needed to boot |

IRIS's O2 support therefore owns a `src/dev/crm/` directory for the graphics
parts (CPU-side geometry/MRE registers and GBE), with `src/dev/crime.rs`
holding the memory/interrupt controller. Nothing in the IP22/IP24/IP28 device
model transfers; the reuse is in the *components inside* those devices (§4).

### 1.1 Physical address map

| Base | Size | Device |
|---|---|---|
| `0x00000000` | 1 GB | RAM bank windows (see §1.2) |
| `0x10000000` | 64 MB | more bank window space |
| `0x14000000` | 512 KB | CRIME CPU interface |
| `0x15000000` | 1 MB | CRIME register file: MRE rasterizer + MTE |
| `0x16000000` | 1 MB | GBE display engine |
| `0x17000000` | 64 KB | VICE (ICE) — not needed to boot |
| `0x18000000` | | PCI I/O window |
| `0x1a000000` | 32 MB | PCI memory window |
| `0x1f000000` | 8 MB | MACE |
| `0x1fc00000` | 1 MB | PROM (512 KB image) |

MACE sub-blocks, offsets from `0x1f000000`:

| Offset | Block |
|---|---|
| `0x080000` | PCI host bridge (config at `+0xcf8`/`+0xcfc`) |
| `0x100000` / `0x180000` | video in 1 / video in 2 |
| `0x200000` | video out |
| `0x280000` | Ethernet (MAC110) |
| `0x300000` | peripheral: audio `+0x00000`, ISA `+0x10000`, PS/2 `+0x20000`, I2C `+00x30000`, UST/MSC `+0x40000` |
| `0x380000` | ISA external: parallel `+0x00000`, serial 1 `+0x10000`, serial 2 `+0x18000`, RTC `+0x20000` |

### 1.2 Memory: 8 CRIME banks and the 1 GB alias

CRIME has eight bank-control registers, `CRM_MEM_BANK_CTRL(0..7)` at
`0x14000000 + 0x208 + i*8`:

```
bits 4:0  bank window address granule, BANK_TO_ADDR = (ctrl & 0x1f) << 25  (32 MB)
bit  8    SDRAM_SIZE: 1 = 128 MB DIMM, 0 = 32 MB DIMM
```

An access matches the **first** control register whose window contains it, with
address bits 31:30 ignored — so every window appears four times, at
`base`, `base + 1 GB`, `base + 2 GB` and `base + 3 GB`. That is the "1 GB
alias": the kernel reaches RAM above 256 MB at `0x40000000 + addr`, and the
PROM probes DIMMs through it (`post1mem.c` maps its probe VAs to
`0x40000000 + va`).

A bank window wraps at its DIMM's real capacity, not at the window size the
register declares — that is what lets the PROM tell a 32 MB DIMM from a 128 MB
one while both registers claim 128 MB (`SDRAM_SIZE` set).

Bank ctrl registers that match bank 0's value are *not* extra memory: the
kernel's `szmem()` skips them, and the PROM's final pass points every empty
register at bank 0's window so that a stray access reports a memory error
instead of silently returning bus noise.

The PROM's final layout (`SizeMEM`, second/third/fourth passes): every 128 MB
bank at the lowest 128 MB granules, then every 32 MB bank above them, then the
empty registers set to bank 0's.

IRIS models this with the existing 4 × `RamBank` (a 4-DIMM O2, i.e. up to
512 MB — everything but the 8 × 128 MB maximum). `Physical` gains an
IP32-specific remap that takes the 8 control registers and resolves
first-match-wins over the four storage banks.

### 1.3 Interrupts

CRIME is the only interrupt controller. `CRM_INTSTAT` (0x10) is
`pending = mask & (soft | hard)`, `CRM_INTMASK` (0x18) gates it, and the
result drives **one** CPU line: `Cause.IP2` (`SR_IBIT3`). `CRM_SOFTINT` (0x20)
is software-written; `CRM_HARDINT` (0x28) is written by the devices:

```
bit  0..15   MACE (see §1.4)
bit 16..19   GBE 0..3
bit 20       CPU error, bit 21 memory error (level-triggered)
bit 22..29   MRE (edge-triggered)
bit 30..31   VICE, software 2
```

CP0 Count/Compare still lands on `Cause.IP7`, as on every other MIPS machine.

### 1.4 MACE interrupts

MACE raises one line into `CRM_HARDINT` bit 3..15 depending on the source
(`mace.h`):

```
MACE_VID_IN_1 0, MACE_VID_IN_2 1, MACE_VID_OUT 2, MACE_ETHERNET 3,
MACE_PERIPH_SERIAL 4, MACE_PERIPH_MISC 5, MACE_PERIPH_AUDIO 6,
MACE_PCI_BRIDGE 7, MACE_PCI_SCSI0 8, MACE_PCI_SCSI1 9,
MACE_PCI_SLOT0/1/2 10..12, MACE_PCI_SHARED0/1/2 13..15
```

Inside MACE, the "ISA" peripherals (RTC, keyboard, mouse, the three MACE
timers, the two UARTs, parallel port, audio) report through
`ISA_INT_STS_REG` (`0x1f310010`) / `ISA_INT_MSK_REG` (`0x1f310018`), and IRIX
groups them into the audio and miscellaneous MACE lines. The PS/2, UART, RTC
and timer interrupts are the ones the PROM and the kernel actually need.

## 2. The PROM

`ip32prom.rev4.18.bin`, 524288 bytes, the same 512 KB flash image for every
O2. Reset vector at `0xBFC00000` (KSEG1 alias of `0x1FC00000`), as on the
other machines. IRIS embeds the **unmodified** image (never a patched one —
users diffing against a real O2's flash must get a byte-identical file) and
falls back to `ip32prom.rev4.18.bin` in the working directory, then the
embedded copy, exactly like `from_file_or_embedded_ip22/ip28`.

### 2.1 Boot sequence and what it needs

1. `csu.s` — uncached PROM copy, BSS, stack; TLB identity map; jump to POST1.
2. POST1 `SizeMEM` (§1.2): probes the 8 banks through the 1 GB alias. Needs
   `CRM_CONTROL`, the 8 bank ctrl regs and working RAM. **A bank-0 failure
   blinks the power LED forever** (`MACE ISA_FLASH_NIC_REG`), so the emulator
   must light the LED rather than spin silently.
3. `finit2`: MACE serial init (writes `ISA_RINGBASE = 0` to take the ISA bus
   out of reset), tiles, then `initGraphics`.
4. `initGraphics` (`crm_init.c`) — the console fork:
   - `console=g` (or the graphics jumper): full init — `initDisplay` (I2C
     monitor ID), `initCrime`, `initGammaMap`, `turnOnGbe`, `initFramebuffer`,
     `initTiming`, `initCursor`.
   - anything else: only `turnOffGbeDma` and two GBE writes (`vt_xy`,
     `ctrlstat`), then the console is the 16550 UART.
5. `initConsole` → POST2 → the PROM menu, on the graphics console or on the
   serial port (`console=d`, `dbaud` for the baud rate).

So the *serial console* path needs only CRIME, MACE ISA/UART/RTC/PS2/I2C/UST
and a GBE that answers its ID — no MRE, no framebuffer. That is the first
milestone; the graphics console (§3) follows.

### 2.2 Console selection without flash writes

The env lives in the PROM flash itself, and flash persistence is deliberately
out of scope until the machine works (see §6). Rather than ship a patched
image, IRIS seeds the env segment in the loaded image before the CPU starts —
the same backdoor-injection pattern the Indigo2 already uses for the Ethernet
MAC (`Hpc3`/`Eeprom93c56::backdoor_set_mac_if_blank`). `[machine] console`
(`g` or `d`) is the knob; the default is `d` until the graphics console
exists, then flips to `g`. It is documented as "the emulator's equivalent of a
machine that was previously `setenv`'d", not as hardware behaviour.

## 3. Graphics: `src/dev/crm/`

The O2's graphics are one ASIC in one directory, mirroring how
`src/dev/ng1/` (Newport), `src/dev/gr2/` and `src/dev/mgras/` each own a
board:

| File | Contents |
|---|---|
| `crm/crime_re.rs` | CRIME's register file at `0x15000000`: interface buffer, TLB, pixel pipe / MRE rasterizer, MTE, status |
| `crm/gbe.rs` | GBE: video timing, tile lists, WID/DID, cmap/gamma, cursor |

The MRE's *3D* pipeline (geometry, texture mapping, shading) is a later step.
What the PROM's textport (`crm_tp.c`) and IRIX's early console actually use is
the **2D path**:

- `BufMode.src/dst`, `DrawMode` (`ENPIXXFER`, `ENLOGICOP`, `ENCOLORMASK`,
  `ENCOLORBYTEMASK`, `ENSMOOTHSHADE`), `ColorMask`, `LogicOp`
- `PixelXfer.src.{xStep, yStep, addr}` — the source pixel transfer address
- `Primitive` (`PRIM_OPCODE_RECT` + edge direction) and `Vertex.X[0..2]`
- `crmSetAndGo` on `PixelXfer.src.addr` / `PixPipeNull` starts the pipe
- MTE for fills and clears: `MTE_MODE`, `MTE_FG_VALUE`, `MTE_DST0/1`,
  `MTE_BYTEMASK`, `MTE_FLUSH`

That is a rectangle blitter with a logic op and a colour mask — the same job
REX3 does for Newport (`src/dev/ng1/rex3.rs`), and the existing
`disp::Rex3Screen` + `Compositor` pipeline presents the framebuffer the same
way, so GBE gets a screen for free.

## 4. What IRIS already has, and where it goes

The point of this section: almost nothing is written from scratch.

| O2 component | Reused IRIS code |
|---|---|
| CPU (R5000 / RM7000 / R10000) | `src/cpu/` — R5000Cache is the O2's default; the PROM accepts impl 0x23/0x27/0x28 and treats them alike |
| JIT v2, ppmem fast path, per-device locking | unchanged |
| CRIME memory controller | the `MemoryController` *shape*: a register device that owns the bank config and calls back into `Physical::remap_banks` |
| MACE 16550 UARTs | `z85c30::SerialBackend` (TCP/CI/Tee backends) with a new 16550 register face |
| MACE PS/2 keyboard + mouse | `dev::ps2::Ps2Controller` verbatim; MACE_KBDMS is a register wrapper, exactly as IOC2's PS/2 registers are |
| MACE RTC (DS17287) | `dev::ds1x86` — same MC146818 core, new register stride |
| MACE UST/MSC timers | `dev::timer` / `TimerManager` |
| AIC-7880 SCSI | the disk layer behind `wd33c93a` (CHD/COW/ISO/changer) behind a PCI register face |
| MACE Ethernet (MAC110) | the NAT/pcap network stack behind a ring-DMA register face |
| GBE display | `disp::Rex3Screen`, `compositor`, `vc2_timings` timing tables, cmap/xmap/bt445 colour maps, NG1's DID/overlay logic |
| VICE (ICE) | not implemented — see §5 |

## 5. VICE

VICE/ICE is the O2's video compression engine. Its registers live at
`0x17000000` and IRIX is its only user: nothing in the PROM, NetBSD or Linux
touches it. It is therefore **out of scope for boot**, and lands last (or
never) as a standalone device — an unimplemented VICE reads as all
ones and raises no interrupt, which is exactly what a machine without the
option board looks like.

## 6. Flash persistence (deliberately deferred)

The PROM's `setenv` writes the env segment back into the flash, gated by
`ISA_FLASH_NIC_REG`'s `FLASH_WE` bit, with the first 0x4000 (boot block)
write-protected and a read-back verify. That is the O2's NVRAM.

Deferred until the machine boots, for two reasons: it is not needed to boot,
and it must not become a way to redistribute a modified SGI firmware image.
When it lands, the sidecar stores **only the bytes the guest actually
changed** (offset + length + data, plus a header identifying the pristine
image by length and checksum), never a copy of the whole 512 KB image — the
same rule that keeps the embedded array legal keeps the sidecar legal.

## 7. PR sequence

Each step compiles, passes `cargo test --workspace`, and leaves the tree
bisectable: a checkout at any commit builds and the previous step's
behaviour is unchanged.

1. **`o2: add the IP32 profile, embed the 4.18 PROM`** — `MachineProfile::O2Ip32`,
   `MachineProfile::ALL`, label, predicates, config validation (32/128 MB
   banks, R5000/R10000 CPUs, GBE graphics), `prombinip32.rs`,
   `Prom::from_file_or_embedded_ip32`, `[machine] console` seed, docs, tests.
   No machine wiring yet: selecting the profile picks the right PROM and
   nothing else changes.
2. **`o2: CRIME — memory banks, interrupts, timer`** — `src/dev/crime.rs`,
   the IP32 physical map in `physical.rs`, 8-bank first-match remap with the
   1 GB alias, `Cause.IP2` wiring, `CRM_TIME` at 66.6665 MHz, profile tests
   for the bank layout the PROM programs.
3. **`o2: MACE ISA — UART, RTC, PS/2, I2C, UST`** — `src/dev/mace.rs` with
   the ISA block, two 16550s on `SerialBackend`, DS17287 on the ds1x86 core,
   `Ps2Controller`, UST/MSC, `ISA_INT_STS/MSK` → CRIME. First boot: the PROM
   sizes memory and reaches its menu on the serial port.
4. **`o2: GBE display`** — `src/dev/crm/gbe.rs` timing/tile/WID/DID/cmap/
   gamma/cursor + `disp` integration.
5. **`o2: CRIME MRE 2D path`** — `src/dev/crm/crime_re.rs`, MTE +
   pixel pipe, so the PROM's textport draws. Graphics console complete.
6. **`o2: MACE PCI bridge + AIC-7880`** — config space, windows, IRQ routing;
   boot IRIX from a CHD disk.
7. **`o2: MACE Ethernet (MAC110)`** — ring DMA on the existing network stack.
8. **`o2: audio, video in/out`** — AD1843 + MACE audio rings; VIN/VOUT.
9. **`o2: flash env persistence`** — per §6.
10. **`o2: VICE`** — per §5.

## 8. Open questions

- `CRM_ID` reads `0xa0 | rev`; the revision nibble the O2 reports is taken
  from the CRIME manual, not yet cross-checked against the PROM (which only
  looks at the GBE's `ctrlstat` revision, `0x000000a1`).
- The O2's R5000 carries a 1 MB secondary cache; IRIS's `R5000Cache` models
  none (Indy's R5000). The PROM reads `Config` rather than the EEPROM's
  CACHSZ on IP32, so this is cosmetic for boot but matters for IRIX's
  cache-flush timing later.
- MACE's PCI memory window (`0x1a000000`, 32 MB) vs. the AIC-7880's register
  and SCRATCH memory needs to be measured against what IRIX programs.
